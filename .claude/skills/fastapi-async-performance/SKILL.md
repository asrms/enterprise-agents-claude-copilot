# Skill: Async Performance in FastAPI

## Implementation Rules:
- **[MANDATORY]** Use `async def` for routes and dependencies only if all the I/O inside them is awaitable (`httpx.AsyncClient`, SQLAlchemy `AsyncSession`, `redis.asyncio.Redis`, `AsyncAnthropic`): a single blocking call inside `async def` stalls the worker's entire event loop and every in-flight request.
- **[FORBIDDEN]** Inside `async def`: `requests.*`, `time.sleep`, synchronous `httpx.Client`, sync DB drivers (`psycopg2`, `pymysql`), sync SDKs (`anthropic.Anthropic`), `open().read()` on large files, CPU-bound work (PDF parsing, OCR, `bcrypt` hashing, tokenizing large corpora).
- **[PATTERN]** Unavoidable sync libraries run outside the event loop with `await run_in_threadpool(func, *args)` (`fastapi.concurrency`) or `await anyio.to_thread.run_sync(func, *args, limiter=pdf_limiter)` with a dedicated `anyio.CapacityLimiter`: anyio's default limiter has 40 tokens shared with all `def` routes and dependencies.
- **[PATTERN]** Routes that use only synchronous libraries are declared `def` (FastAPI runs them in the threadpool) instead of `async def` with blocking calls inside.
- **[PERFORMANCE]** CPU-bound work beyond ~50 ms per request (local embeddings, OCR, document conversion) goes outside the web process: `anyio.to_process.run_sync` only for occasional cases, otherwise a dedicated task queue (Arq, Celery) with separate workers.
- **[MANDATORY]** A single `httpx.AsyncClient` per upstream, created in the `lifespan` and closed with `await client.aclose()`; never `async with httpx.AsyncClient()` per request, which defeats connection pooling and repeats TCP/TLS handshakes on every call.
- **[CONFIGURATION]** Client configured explicitly from `Settings`: `httpx.Timeout(10.0, connect=2.0, pool=1.0)` and `httpx.Limits(max_connections=100, max_keepalive_connections=20, keepalive_expiry=30.0)`; httpx defaults (5 s timeout, 100 connections) are not tuned to the upstream SLA and must not be left implicit.
- **[PERFORMANCE]** Backpressure toward expensive upstreams (LLMs, legacy services) with `asyncio.Semaphore(settings.llm.max_concurrency)` created in the lifespan; acquisition has a timeout (`async with asyncio.timeout(settings.llm.queue_timeout_s): await semaphore.acquire()`) and, when it expires, respond 503 with a `Retry-After` header instead of queuing indefinitely.
- **[PATTERN]** Concurrent fan-out with `asyncio.TaskGroup` (Python 3.11+) instead of `asyncio.gather` without error handling: a failure cancels sibling tasks, and errors arrive as an `ExceptionGroup`, to be inspected with `eg.subgroup(...)` or `except*`.
- **[FORBIDDEN]** Fire-and-forget `asyncio.create_task(...)` without keeping the reference or handling exceptions: the task can be garbage-collected and errors are lost; use `TaskGroup`, `BackgroundTasks`, or a task queue.
- **[PERFORMANCE]** Incrementally generated responses (LLM tokens, CSV exports) with `StreamingResponse(generator, media_type="text/event-stream")`; the generator stops upstream work when the client disconnects (`await request.is_disconnected()`, `contextlib.aclosing`) so as not to waste tokens and connections.
- **[CONFIGURATION]** SSE headers `Cache-Control: no-cache` and `X-Accel-Buffering: no` (disables Nginx buffering); a `: ping\n\n` heartbeat every ~15 s when the load balancer has an idle timeout shorter than the stream duration.
- **[PATTERN]** `BackgroundTasks.add_task(...)` only for short, idempotent, losable work (non-critical auditing, cache invalidation, metrics): it runs in the same process after the response and is lost on crash, redeploy, or scale-in.
- **[MANDATORY]** Heavy jobs or jobs that must survive a restart (long document summarization, batch classification, RAG ingestion) go on a task queue: Arq (`await arq_pool.enqueue_job("summarize_document", document_id, _job_id=f"summarize:{document_id}")`) or Celery; the route responds `202 Accepted` with a `job_id` and a status endpoint.
- **[PERFORMANCE]** Async SQLAlchemy: `create_async_engine(url, pool_size=10, max_overflow=5, pool_timeout=5, pool_pre_ping=True)` and `async_sessionmaker(engine, expire_on_commit=False)`; relationships loaded with `selectinload()` to avoid implicit lazy loading (`MissingGreenlet`); `(pool_size + max_overflow) × workers × replicas` must stay below the database's `max_connections`.
- **[CONFIGURATION]** Worker sizing for I/O-bound async services: roughly 1 worker per vCPU (the `2n+1` formula is meant for sync workers); in Kubernetes, prefer 1 worker per pod and scale with HPA. Startup: `uvicorn app.main:app --workers N --proxy-headers --forwarded-allow-ips=<load balancer cidr> --timeout-graceful-shutdown 30`.
- **[CONFIGURATION]** With gunicorn: `gunicorn app.main:app -k uvicorn_worker.UvicornWorker -w 4 --graceful-timeout 30 --timeout 60 --max-requests 1000 --max-requests-jitter 100` (`uvicorn-worker` package; `uvicorn.workers.UvicornWorker` is deprecated since uvicorn 0.30).
- **[PERFORMANCE]** Load shedding at the server level too, with `uvicorn --limit-concurrency 200` (above the threshold it responds 503), consistent with application semaphores and readiness probes.
- **[PERFORMANCE]** Cache expensive results shared across workers in Redis (`redis.asyncio.Redis`) with an explicit TTL (`await redis.set(key, value, ex=ttl_s)`); `functools.lru_cache` only for immutable process-level values (settings), never for per-user data.
- **[TESTING]** Detect event loop blocking in tests and staging with `PYTHONASYNCIODEBUG=1` (flags callbacks exceeding `loop.slow_callback_duration`, default 0.1 s) and load tests (Locust, k6) with p95/p99 thresholds before every release.
