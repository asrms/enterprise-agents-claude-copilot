# Skill: Hexagonal Architecture with Spring Boot (Ports & Adapters)

## Implementation Rules:
- **[ARCHITECTURE]** Organize every bounded context into `<base>.<context>.domain` (model, service, event), `<base>.<context>.application` (`port.in`, `port.out`, use cases), and `<base>.<context>.adapter` (`in.web`, `in.messaging`, `out.persistence`, `out.messaging`, `out.client`), plus a `config` package for wiring; no cross-cutting technical packages such as `controllers`/`repositories` at root level.
- **[ARCHITECTURE]** Enforce the dependency rule: `adapter` → `application` → `domain`; `domain` imports nothing from `application`, `adapter`, or `config`, and `application` imports nothing from `adapter`.
- **[FORBIDDEN]** The `domain` package must not import from `org.springframework..`, `jakarta.persistence..`, `jakarta.validation..`, `com.fasterxml.jackson..`, or `org.hibernate..`: no `@Entity`, `@Component`, `@Service`, `@Transactional`, or `@JsonProperty` on domain classes.
- **[MANDATORY]** Model aggregates as classes with protected invariants (a validating constructor/`create(...)` factory, no public setters, behavior methods such as `order.confirm()`), and value objects as immutable Java 21 `record` types with validation in the compact constructor (e.g., `record Money(BigDecimal amount, Currency currency)`).
- **[PATTERN]** Define one inbound port per use case (`interface PlaceOrderUseCase { OrderId place(PlaceOrderCommand command); }`) with commands/queries as `record` types; the controller depends only on the interface, never on the implementation.
- **[PATTERN]** Define outbound ports in the `application.port.out` package with domain-oriented names (`LoadOrderPort`, `SaveOrderPort`, `PublishOrderEventPort`) that accept and return domain types, never JPA entities, Spring Data `Page`, or `ResponseEntity`.
- **[PATTERN]** Implement the use case in an `application` class (e.g., `PlaceOrderService implements PlaceOrderUseCase`) with constructor injection of the ports only; the transactional boundary (`@Transactional`) belongs on the application use case, never in the domain or the controller.
- **[MANDATORY]** Keep three distinct models with explicit mapping at the boundaries: web DTOs (`record` types in `adapter.in.web`), the domain model, and JPA entities (`adapter.out.persistence`); mapping happens in the adapter through a dedicated mapper (MapStruct with `componentModel = "spring"` or static `toDomain`/`fromDomain` methods).
- **[FORBIDDEN]** Do not expose Spring Data repositories (`JpaRepository`) outside the persistence adapter: the `OrderPersistenceAdapter implements LoadOrderPort, SaveOrderPort` adapter encapsulates repositories and entities, which are declared package-private.
- **[PATTERN]** Express alternative domain outcomes with `sealed interface` + `record` (e.g., `sealed interface PaymentResult permits Authorized, Declined, RequiresAction`) and handle them with exhaustive `switch` pattern matching, without a `default` branch, instead of boolean flags or exceptions for control flow.
- **[PATTERN]** Throw specific domain exceptions (`OrderNotFoundException`, `InsufficientStockException`) that extend an unannotated `DomainException`; translation into HTTP status codes happens only in the web adapter via `@RestControllerAdvice`.
- **[CONFIGURATION]** Register pure domain services (without annotations) as beans in a `@Configuration` class of the `config` package through `@Bean` methods, instead of annotating them with `@Service`.
- **[ARCHITECTURE]** Publish domain events as immutable `record` types collected by the aggregate (`List<DomainEvent> pullEvents()`) and forwarded by the use case to the `PublishOrderEventPort` port; the domain knows nothing about `ApplicationEventPublisher` or Kafka.
- **[SECURITY]** Role-based authorization decisions (`@PreAuthorize`) belong on inbound adapters or application use cases; business ownership rules (e.g., "only the owning customer can cancel the order") are domain invariants that receive the identity as a value object (`CustomerId`).
- **[PERFORMANCE]** Design read ports for queries (lightweight CQRS) that return dedicated read models (`record OrderSummaryView`) directly from adapter projections, instead of hydrating the full aggregate just to display lists.
- **[TESTING]** Apply ArchUnit (`com.tngtech.archunit:archunit-junit5`) with `@AnalyzeClasses(packages = "<base>", importOptions = ImportOption.DoNotIncludeTests.class)` and `@ArchTest` rules for: a Spring/JPA-free domain, `layeredArchitecture()` or `onionArchitecture()`, and no cycles via `slices().matching("<base>.(*)..").should().beFreeOfCycles()`.
- **[TESTING]** Test the domain and use cases with plain JUnit 5 unit tests without a Spring context (no `@SpringBootTest`), using in-memory fakes or mocks of the outbound ports; every domain test must run in under 100 ms.
- **[TESTING]** Test each adapter in isolation with the appropriate test slice: `@WebMvcTest(OrderController.class)` with `@MockitoBean` on the use case, `@DataJpaTest` + Testcontainers for the persistence adapter.
- **[CONFIGURATION]** For modular monoliths, evaluate Spring Modulith (`spring-modulith-starter-core`) and verify module boundaries with `ApplicationModules.of(Application.class).verify()` in a dedicated test, in addition to or instead of ArchUnit.
- **[REFERENCE]** See `EXAMPLES.md` in this folder for reference anti-patterns and best practices.
