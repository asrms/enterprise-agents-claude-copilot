# Skill: Relational Data Modeling

## Implementation Rules:
- **[ARCHITECTURE]** Model from the domain and the access patterns: start in third normal form to remove update anomalies, then denormalize deliberately (read models, materialized views, cached aggregates) only for measured read-performance needs, documenting how the copy stays consistent.
- **[MANDATORY]** Every table has a primary key; prefer surrogate keys (`bigint GENERATED ALWAYS AS IDENTITY`, or UUIDv7/ULID when ids are generated by clients or must not be enumerable) and enforce natural business keys with `UNIQUE` constraints (`UNIQUE (tenant_id, sku)`).
- **[MANDATORY]** Let the database enforce integrity: `NOT NULL` by default, `CHECK` constraints for domain rules (`CHECK (quantity > 0)`, `CHECK (status IN (...))`), `FOREIGN KEY` constraints with an explicit `ON DELETE` behavior, and `UNIQUE` constraints for business uniqueness; application validation complements but does not replace them.
- **[MANDATORY]** Correct types: money as `numeric(19,4)` (or integer minor units) plus an ISO 4217 currency column, never `float`/`double`/`money`; timestamps as `timestamptz` (PostgreSQL) or `datetime2`/`DATETIMEOFFSET` stored in UTC; dates without time as `date`; booleans as `boolean`; text as `text`/`varchar(n)` with a length only when it is a real rule; JSON as `jsonb` only for genuinely schemaless attributes.
- **[PATTERN]** Naming conventions: `snake_case`, plural or singular table names consistently, `id` for the primary key, `<entity>_id` for foreign keys, constraint and index names that describe them (`fk_order_line_order`, `uq_product_tenant_sku`, `ix_order_customer_created`).
- **[PATTERN]** Status and type columns use a lookup table or a `CHECK`-constrained text/enum type; prefer text with `CHECK` over native enum types when values change frequently (adding enum values requires migrations in some engines).
- **[PATTERN]** Audit columns on business tables: `created_at`, `updated_at` (maintained by the application or a trigger), `created_by`/`updated_by` where accountability is required, and a `version` column for optimistic locking.
- **[PATTERN]** Soft delete (`deleted_at`) only when there is a business need to restore or audit; it complicates every query and unique constraint (use partial unique indexes `WHERE deleted_at IS NULL`) and conflicts with erasure obligations; otherwise hard delete plus an audit/event log.
- **[ARCHITECTURE]** Multi-tenancy: choose explicitly between database per tenant, schema per tenant, and shared tables with a `tenant_id` column; with shared tables, `tenant_id` is part of unique constraints and indexes, and Row-Level Security policies enforce isolation.
- **[PATTERN]** Many-to-many relations use a junction table with a composite primary key or a unique constraint on both foreign keys, plus its own attributes when the relationship has data (quantity, role, valid_from).
- **[PATTERN]** Temporal data: history tables or `valid_from`/`valid_to` ranges with exclusion constraints (`EXCLUDE USING gist (product_id WITH =, valid_period WITH &&)`) for prices, contracts, and assignments that change over time.
- **[FORBIDDEN]** Entity-Attribute-Value designs for core data, comma-separated lists in columns, polymorphic foreign keys without constraints (`owner_type` + `owner_id`), and reserved words or case-sensitive quoted identifiers as names.
- **[SECURITY]** Classify columns containing personal or sensitive data in the schema documentation (or comments), minimize what is stored, and separate highly sensitive data (payment references, health data) into tables with stricter access.
- **[TESTING]** Constraints are tested: integration tests insert invalid data and expect constraint violations, and migrations are applied to a real database of the same engine in CI.
