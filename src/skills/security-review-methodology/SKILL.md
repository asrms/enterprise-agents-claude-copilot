# Skill: OWASP Security Code Review Methodology

## Implementation Rules:
- **[ARCHITECTURE]** Define the scope before reading code: repository, branch and commit (`git rev-parse HEAD`), in-scope and out-of-scope components, languages and frameworks detected with `Glob` on `pom.xml`, `build.gradle*`, `package.json`, `pyproject.toml`, `requirements*.txt`; record everything in the report's "Scope and Methodology" section together with limitations (e.g., generated code, third-party services not visible).
- **[ARCHITECTURE]** Build the data flow starting from entry points: Spring `@RestController`/`@RequestMapping`/`@KafkaListener`/`@Scheduled`, FastAPI `@app.<verb>`/`APIRouter`, Express `router.<verb>`/NestJS `@Controller`, queue consumers, file uploads, inbound webhooks; map the trust boundaries (internet→gateway, gateway→service, service→DB, service→third parties, service→cloud metadata).
- **[PATTERN]** Apply STRIDE to every trust boundary and, for each threat, record the expected control and whether it is present: Spoofing→A07, Tampering→A03/A08, Repudiation→A09, Information disclosure→A01/A02, Denial of service→rate limit/timeout, Elevation of privilege→A01.
- **[PATTERN]** Trace untrusted sources (`@RequestParam`, `@RequestBody`, `@PathVariable`, `@RequestHeader`, `@CookieValue`, `request.query_params`, `await request.json()`, `req.body`, `req.query`, `req.params`, `req.headers`, queue messages, uploaded files, external API responses) to the sinks (`createNativeQuery`, `Statement.execute`, `Runtime.exec`, `ProcessBuilder`, `subprocess`, `child_process.exec`, `eval`, `res.send` with HTML, `requests.get`/`fetch`/`RestTemplate`, `ObjectInputStream`, `pickle.loads`, `yaml.load`, `DocumentBuilderFactory`, filesystem APIs).
- **[MANDATORY]** An injection, SSRF, deserialization, or path traversal finding requires the complete chain source→missing neutralization→sink with the `file:line` of every step; if any link cannot be verified, the finding goes to "Needs Verification" with Low confidence.
- **[MANDATORY]** Use OWASP ASVS 4.0.3 Level 2 as the default checklist (Level 3 for payments, healthcare, critical infrastructure) and state the version in the report; map controls to chapters V2 Authentication, V3 Session, V4 Access Control, V5 Validation/Encoding, V6 Cryptography, V7 Error/Logging, V8 Data Protection, V9 Communications, V12 Files, V13 API, V14 Configuration.
- **[MANDATORY]** Run SAST with explicit rulesets and telemetry disabled: `semgrep scan --metrics=off --config p/owasp-top-ten --config p/java --config p/python --config p/typescript --config p/secrets --json --output <dir>/semgrep.json`; every result is a lead to confirm with Read, never an automatic finding.
- **[MANDATORY]** Run SCA for A06 on every ecosystem present: `dependency-check.sh --scan . --format JSON --out <dir>` (Java), `trivy fs --scanners vuln,secret,misconfig --format json --output <dir>/trivy.json .`, `npm audit --omit=dev --json`, `pip-audit -r requirements.txt --no-deps --disable-pip -f json -o <dir>/pip-audit.json`; for each component report CVE, installed version, fixed version, and reachability (is the vulnerable function actually invoked?).
- **[FORBIDDEN]** Running `npm install`, `pip install`, builds with third-party scripts, the application itself, or exploits against real environments during the review: Bash is used only for read-only scanners, `grep`, `git log`, `git blame`, `git diff`.
- **[MANDATORY]** Finding format: ID `SEC-NNN`; title "vulnerability + component/endpoint"; severity with score and full vector `CVSS:3.1/AV:_/AC:_/PR:_/UI:_/S:_/C:_/I:_/A:_`; most specific CWE (CWE-89, not CWE-20); category `A0x:2021-<Name>`; location `path/relative/File.ext:line` or range; evidence (real snippet ≤ 15 lines); impact (prerequisites and what the attacker gains); remediation with corrected code in the project's language; references (Cheat Sheet, ASVS, CWE); confidence High/Medium/Low.
- **[FORBIDDEN]** Findings based on "seems", "might", on a file or function name alone, on unverified tool output, or on dependency versions with no associated CVE; never report already-mitigated patterns (`PreparedStatement` with `?`, `yaml.safe_load`, `execFile` with an array, `th:text`) except as Informational when a regression risk is documented.
- **[PATTERN]** Derive severity from the CVSS v3.1 base score: Critical 9.0–10.0, High 7.0–8.9, Medium 4.0–6.9, Low 0.1–3.9, Informational 0.0; context (internet exposure, data handled, compensating controls) changes the remediation priority, justified in writing, not the base score.
- **[PATTERN]** Confidence: High = source→sink chain verified end-to-end; Medium = dangerous sink with plausibly controllable input but one untraced step (reflection, runtime configuration); Low = depends on conditions not observable in the code; Low-confidence items go only in "Needs Verification".
- **[PATTERN]** Deduplicate by root cause: the same defect in N places = a single finding listing every `file:line` occurrence; different defects in the same file = separate findings.
- **[REVIEW]** On pull requests, scope with `git diff --name-only origin/main...HEAD`, but follow the flow into calling and called code outside the diff; use `git log -p -S '<pattern>'` to check whether a removed secret or sink is still in the history.
- **[REVIEW]** Always run targeted greps with vendor exclusions: `--exclude-dir={node_modules,.git,target,build,dist,.venv,vendor}` and `--include` per language; save the `file:line` lists in a triage queue kept separate from the report.
- **[SECURITY]** For discovered secrets, show at most the first 4 characters and the length in the report (e.g., `AKIA…`, 20 characters), never the full value; recommend immediate rotation even if the secret has been removed from the current branch.
- **[PERFORMANCE]** Reading priority: internet-exposed entry points, authentication, authorization, URL/file/XML/deserialization handling, then everything else; on repositories with more than 5,000 files, start from sink greps and Read only the relevant ranges (`offset`/`limit`) instead of whole files.
- **[TESTING]** For every High/Critical finding, the remediation includes an automated test that fails on the vulnerable code (e.g., user B requesting A's resource receives 404; `sort=(SELECT 1)` receives 400); also check whether security tests exist and flag their absence in the ASVS controls.
- **[CONFIGURATION]** Include configuration and IaC in scope: `application*.yml`/`.properties`, `.env*`, `Dockerfile`, `docker-compose*.yml`, Kubernetes/Helm manifests, Terraform (`trivy config .`), CI workflows (`.github/workflows/*.yml` with `pull_request_target` running PR code, `permissions: write-all`).
- **[MANDATORY]** Report structure: 1) Executive Summary ≤ 10 lines with a count per severity, the top 3 risks, and a go/no-go recommendation; 2) Scope and Methodology; 3) Summary Table (ID, title, severity, CVSS, CWE, OWASP, confidence) sorted by severity; 4) Detailed Findings; 5) Vulnerable Components (SCA); 6) Needs Verification; 7) Appendix with the ASVS controls verified and the discarded automated results with rationale.
- **[CWE]** Reference mapping: CWE-89/CWE-78/CWE-79 → A03; CWE-639/CWE-862/CWE-863/CWE-22 → A01; CWE-327/CWE-328/CWE-321/CWE-338 → A02; CWE-287/CWE-307/CWE-384/CWE-798 → A07; CWE-502/CWE-915 → A08; CWE-611/CWE-942 → A05; CWE-117/CWE-532/CWE-778 → A09; CWE-918 → A10; CWE-1104/CWE-1395 → A06.
- **[REFERENCE]** See `EXAMPLES.md` in this folder for reference anti-patterns and best practices.
